#### **동시 요청 상황에서 거래완료·좋아요 정합성이 깨지는 문제를 재현하고 락 전략을 실측 비교해 해결**

**전체적인 아키텍처**

**문제 원인**

- 코드 리뷰 중 completeTrade(거래완료 처리)가 락이나 상태 체크 없이 buyer 필드를 그대로 덮어쓰는 것을 발견 — 동시에 두 구매자가 거래완료를 시도하면 실제 거래 상대방 정보가 조용히 다른 사람으로 바뀔 수 있는 구조로, 이커머스의 재고 이중 판매(overselling)와 같은 급의 정합성 문제
- JUnit + ExecutorService/CountDownLatch로 구매자 2명이 동시에 거래완료를 시도하는 상황을 실제 재현한 결과, 둘 다 성공 처리되고 최종 buyer가 나중에 커밋된 요청으로 조용히 덮어써짐을 확인. 같은 방식으로 동일 상품에 20명이 동시에 좋아요를 요청하자 대부분이 유실되어 20건 중 1건만 반영됨을 확인

**해결 과정**

- 거래완료는 호출 빈도가 낮고 재시도를 요구하기 어려운 액션이라, 비관적 락으로 동시 요청을 직렬화하고 이미 완료된 거래의 재처리를 막는 상태 가드를 추가
- 좋아요는 호출 빈도가 높고 실패 비용이 낮아 낙관적 락(@Version) + 재시도를 채택. 다만 인기 상품처럼 요청이 몰리면 버전 충돌 이전에 InnoDB 데드락으로 실패하는 사례가 실측에서 드러나, 재시도 대상 예외를 낙관적 락 실패와 데드락의 공통 상위 타입(ConcurrencyFailureException)까지 넓혀 해결
- 동일 조건(동시 요청 20건)에서 두 락 전략의 처리량을 직접 비교 측정하고, 락 예외가 500으로 새어나가지 않도록 전역 예외 처리기를 정리

**결과**

- 구매자 2명이 동시에 거래완료를 시도한 경우, 정확히 1명만 성공(수정 전: 2명 다 성공, buyer 덮어써짐)하도록 개선해 이중 거래 사고를 원천 차단
- 동일 상품에 20명이 동시에 좋아요를 요청한 경우, 20건 모두 정확히 반영(수정 전: 20건 중 1건만 반영)되도록 정합성 확보
- 동일 조건(동시 요청 20건)에서 낙관적+재시도 vs 비관적 락의 처리량을 301ms vs 60ms로 실측 비교
- 재현·검증 과정을 자동화 테스트로 남겨, 정합성 검증을 반복 가능하게 만들고 테스트 커버리지 공백도 보완
