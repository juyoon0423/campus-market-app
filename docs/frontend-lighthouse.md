# 프론트엔드 Lighthouse 측정 기록

프론트 화면 리팩토링(브랜치 `feat/frontend-redesign`) 전후의 성능, 접근성 수치를 비교하기 위한 기록이다.
지금까지 이 프로젝트에는 프론트 성능 수치 기록이 없었다. 그래서 리팩토링 전 측정값이 첫 기준선이 된다.
**전후 비교는 아래 조건을 똑같이 맞췄을 때만 의미가 있다.** 조건을 바꿔야 하면 이 문서에 먼저 적고, 전과 후를 둘 다 다시 잰다.

## 1. 측정 조건 (2026-11-17 확정, 전후 동일 적용)

### 로컬 실행에 필요한 것
| 구성 | 필요 여부 | 비고 |
|---|---|---|
| MySQL 8 (`campus_market`) | 필요 | 로컬 설치본 사용 |
| Redis (6379) | 필요 | 목록 캐시(`products`, TTL 10분). 측정 때는 영속화를 끄고 띄움(`--save "" --appendonly no`) |
| Elasticsearch | 불필요 | 백엔드에 의존성 없음. 목록은 MySQL(QueryDSL) + Redis 캐시 |
| OpenAI 키 | 불필요 | AI 설명 생성은 Gemini(`GEMINI_API_KEY`)를 쓴다. 측정 화면에서는 호출하지 않음 |
| 카카오맵 JS 키 | 필요 | `frontend/.env.local`의 `NEXT_PUBLIC_KAKAO_MAP_KEY`. 상세, 등록, 수정 화면의 지도 |
| 카카오 OAuth | 측정에는 불필요 | 로그인 화면의 "카카오로 시작하기" 버튼은 이동만 한다 |
| Gmail 앱 비밀번호 | 측정에는 불필요 | 회원가입 인증번호 발송용 |

- 라이브 데모 백엔드는 꺼져 있어서 모두 로컬에서 잰다.

### 빌드와 서버
- **프로덕션 빌드**로 잰다: `cd frontend && npm run build && npm run start` (http://localhost:3000). 개발 서버는 번들이 압축되지 않아서 쓰지 않는다.
- 백엔드는 `cd backend && ./gradlew bootRun`(http://localhost:8080)으로 띄운다. `/products/[id]` 측정에 필요하다.

### 측정 도구
- **Lighthouse CLI 13.6.0**(`npx lighthouse@13.6.0`) + **Chrome 157**(headless). InsightStock 측정과 같은 버전이다.
- Lighthouse CLI는 측정할 때마다 임시 프로필로 새 Chrome을 띄운다. 캐시, 쿠키, localStorage가 비어 있어서 **비로그인 상태**로 잰다.
- **모바일**: Lighthouse 기본값(Moto G Power 에뮬레이션, 느린 4G, CPU 4배 감속). **데스크톱**: `--preset=desktop`.
- 카테고리: Performance, Accessibility, Best Practices, SEO.
- **페이지마다 모바일과 데스크톱 각각 3회씩 재서 중앙값**을 기록한다.
- 측정 중에는 빌드나 테스트 같은 무거운 작업을 동시에 돌리지 않는다.

```bash
npx lighthouse@13.6.0 http://localhost:3000/ \
  --only-categories=performance,accessibility,best-practices,seo \
  --chrome-flags="--headless=new" \
  --output=json --output=html --output-path=<저장경로>/<페이지>-mobile-1
# 데스크톱은 --preset=desktop 추가
```

### 성능: 원인은 글꼴 파일 하나
- 세 페이지 모두 가장 큰 요청은 **`PretendardVariable.woff2` 2,010KB**다. 2026-08 UI 리뉴얼(`90eb2d0`)에서 `next/font/local`로 넣은 전체 가변 글꼴이다.
  - 한글 전 글자와 굵기 45~920 전체가 파일 하나에 들어 있다.
  - `next/font`가 모든 페이지에서 미리 불러온다(preload).
- 텍스트만 있는 `/login`도 전송량이 2,246KB이고, 그중 약 90%가 이 글꼴이다.
- FCP는 0.75초로 빠르다. 하지만 `font-display: swap`으로 OS 글꼴로 먼저 그린 뒤, 느린 4G에서 2MB가 다 받아지면 글자를 다시 그린다. 이 시점이 LCP로 기록된다(모바일 12.6~13.5초).
- `/login` 모바일 Performance가 75/100/75로 흔들린다. 3회 중 1회는 글꼴 도착 전에 LCP가 확정된 것으로 보인다.
- InsightStock에서 IBM Plex Sans KR을 넣었을 때 LCP가 0.76초에서 8.95초로 늘어난 것과 같은 현상이다. 이 프로젝트에는 이미 들어가 있었다.

## 3. 중간: 글꼴만 변경 (2026-11-17 측정)

화면 리팩토링 전에 **글꼴만** 바꾸고 1절과 같은 조건으로 쟀다. 글꼴 효과와 화면 리팩토링 효과를 구분하려는 것이다. 화면 코드, 색, 레이아웃은 기준선과 같다.

### 3-1. 왜 2MB 파일이 들어가 있었나
- 2026-08 UI 리뉴얼 커밋 `90eb2d0`에서 `next/font/local`로 `pretendard/dist/web/variable/woff2/PretendardVariable.woff2`를 넣었다(`weight: "45 920"`).
  - 이 파일은 한글 전체와 모든 굵기가 들어 있는 **전체 가변 글꼴 하나**(2,058KB)다.
- `next/font`는 지정한 글꼴을 모든 페이지 `<head>`에서 미리 불러온다(preload). 그래서 텍스트만 있는 `/login`도 이 파일을 받았다.
- 당시에는 Lighthouse 측정 기록이 없어서 문제가 드러나지 않았다. 데스크톱(감속 약함)에서는 LCP 0.2~2.4초로 크게 티 나지 않고, 모바일(느린 4G)에서만 12~13초가 됐다.

### 3-2. 비교한 두 방식
| 방식 | 내용 | 외부 요청 |
|---|---|---|
| OS 한글 글꼴 스택 | `-apple-system, BlinkMacSystemFont, "Apple SD Gothic Neo", "Malgun Gothic", "Noto Sans KR", system-ui, sans-serif`. 글꼴 파일을 받지 않는다 | 없음 |
| Pretendard dynamic-subset (자체 호스팅) | 같은 `pretendard` 패키지의 `pretendardvariable-dynamic-subset.css`를 `layout.tsx`에서 import. 92조각 woff2가 빌드 때 `_next/static/media`로 복사되고, 브라우저는 `unicode-range`에 맞는 조각만 받는다 | 없음(모두 localhost:3000) |

판정 기준(사전 결정): dynamic-subset의 LCP가 OS 스택보다 **0.2초 넘게 늦거나**, CLS가 **0.05를 넘으면** OS 스택을 채택한다.

- dynamic-subset은 OS 스택보다 모바일 LCP가 `/`에서 +1.51초, `/products/898`에서 +1.43초, `/login`에서 +0.15초 늦었다. 앞의 두 페이지가 기준(+0.2초)을 넘었다.
  - 상품 목록과 상세는 글자 종류가 많아 조각 10~12개(260~312KB)를 받는다. 느린 4G에서 이 조각들이 상품 사진과 대역폭을 나눠 쓴다.
- 미리 정한 기준대로 OS 스택을 채택했다. 바꾼 곳은 `app/layout.tsx`(`next/font/local` 제거)와 `app/globals.css`(`--font-sans`) 두 파일뿐이다.
- 결과: 모바일 LCP `/login` 12.60초 → 0.75초, 전송량 `/` 2,361KB → 351KB(-85%). CLS는 그대로다.
- 받아들인 단점: OS마다 글꼴이 다르다(맥은 Apple SD Gothic Neo, 윈도는 맑은 고딕).
- `/`와 `/products/898`의 모바일 LCP(3.46초, 3.01초)는 이제 글꼴이 아니라 상품 사진 요청이 차지한다. 화면 리팩토링(첫 화면 이미지 우선순위 등)에서 다시 보고 4절 "후" 측정에서 비교한다.
- `package.json`의 `pretendard` 의존성은 이제 쓰이지 않는다. 의존성 변경은 이번 범위에서 하지 않기로 해서 남겨 두었다(별도 작업 목록).

### 4-2. 모바일 LCP 요소와 이미지 우선 로딩 효과
| 페이지 | LCP 요소 | 중간 → 후 LCP(모바일) | 요청 발견 조건(Lighthouse `lcp-discovery-insight`) 중간 → 후 |
|---|---|---|---|
| `/` | **상품 이미지**: 첫 카드 사진 `img`(184×184, 18KB) | 3.46초 → 3.46초 | `loading=lazy` → eager, fetchpriority 없음 → high. "처음 HTML에서 발견 가능"은 둘 다 아니오 |
| `/products/898` | **상품 이미지**: 대표 사진 `img`(380×380, 34KB) | 3.01초 → 3.01초 | 둘 다 eager, 발견 가능. Next 16에서 `priority`가 deprecated라 `preload`로 바꿨다 |
| `/login` (참고) | 글자: 안내 문단 `p` | 0.75초 → 0.75초 | 이미지 아님 |

- 첫 줄 사진 4장을 지연 로딩에서 빼고 앞 2장에 `fetchPriority="high"`를 줬다. 그 결과 요청 우선순위 High가 0개에서 2개로 바뀌었지만 **LCP 시뮬레이션 값은 그대로**다.
- 이유: 모든 페이지가 `"use client"`(CSR)라 사진 주소는 처음 HTML에 없다. 순서가 HTML → JS 192KB(상세 240KB) → 상품 API → 사진으로 고정되어 있다. 사진 자체는 18~34KB로 작아서, 느린 4G 시뮬레이션에서 LCP를 정하는 것은 이 체인의 앞부분(JS와 API)이다. 우선순위 힌트로는 체인 앞부분을 줄일 수 없다.
- 실제로 줄이려면 첫 페이지 데이터를 서버에서 받아 HTML에 넣어야 한다(서버 컴포넌트나 SSR). 데이터 흐름이 바뀌는 변경이라 이번 범위(화면만 변경)에서 하지 않고 별도 작업으로 남긴다(`docs/frontend-design.md` 5절).
- 우선순위 설정은 되돌리지 않았다. 측정상 손해가 없고(전송량 차이 +9KB 이내, 측정 오차 수준), Lighthouse 발견 체크리스트 3개 중 2개를 통과시킨다.
